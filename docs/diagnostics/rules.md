# Deterministic diagnostic rules

VibeTrace diagnostics are versioned functions over canonical trace events. They do not call a model, infer hidden intent, or assign a universal quality score. Every persisted finding contains at least one existing evidence event ID; any weakening observation is stored separately as a counter-evidence ID.

The daemon analyzes each session after a sealed spool batch is committed. A manual authenticated `POST /api/v1/sessions/:id/analyze` reruns the same engine. Analyzer-owned findings are replaceable. Human confirmation, rejection, category overrides, and notes live in a separate review record keyed by the stable finding ID, so they survive deterministic reruns and temporary disappearance only while the detector version and evidence identity remain unchanged.

## Rules in version 0.1.0

| Rule                                             | Observable trigger                                                                                                                                  | Important boundary                                                                                                                                                                                                                                                         |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No tests after final change                      | The last `file.changed` or per-event changed Git snapshot has no later test attempt.                                                                | Baseline and cumulative final snapshots are not new changes. A failed test still counts as a test attempt.                                                                                                                                                                 |
| Success claim after unresolved failure           | The final observed agent message contains a narrow success phrase while a failure lacks a matching successful command, verification, or tool event. | The matcher rejects explicit negations. Later agent corrections replace an interim claim; the rule reports observable claim/evidence ordering, not truth.                                                                                                                  |
| Repeated identical failed command                | The same tokenized command fails at least twice.                                                                                                    | Equality is token based. Near-equivalent commands are intentionally not guessed.                                                                                                                                                                                           |
| Modified file without observed inspection        | A `file.changed` path has no earlier exact-path `file.read`.                                                                                        | Reads embedded only in opaque command text are not treated as observed file reads.                                                                                                                                                                                         |
| Unresolved error at session end                  | A failure key has no later matching success key before a captured `session.completed` marker.                                                       | Active sessions never emit this finding. Generic errors can be resolved only when the trace exposes a matchable identity.                                                                                                                                                  |
| Pre-existing versus introduced failure           | The same verification has a stable pass/fail state both before and after the first change.                                                          | Mixed or missing baseline evidence remains unknown and produces no classification.                                                                                                                                                                                         |
| Compaction followed by user correction           | `user.steered` occurs after a captured context-compaction boundary.                                                                                 | This is a temporal signal; it does not claim which requirement was forgotten.                                                                                                                                                                                              |
| Skill/instruction contradiction signal           | Contradiction-like user steering follows a loaded skill or instruction.                                                                             | Only a signal is reported because loaded content is represented by name/hash, not reinterpreted by the rule.                                                                                                                                                               |
| Repeated tool-error loop                         | One tool emits at least three structured failures without an intervening successful completion.                                                     | Codex `PostToolUse` responses with nonzero exits, failure statuses, or `isError`/false success flags normalize as failures. Failures without tool identity cannot be grouped.                                                                                              |
| Declined approval followed by equivalent request | A later request has the same canonical tool name and structured input as a declined request.                                                        | A canonical `permission.resolved` event or a declined terminal tool event is required. The Codex hook contract exposes `PermissionRequest` before the user decision but no resolution hook, so the adapter emits an approval capture gap when no terminal evidence exists. |
| Large code churn relative to task                | Added/deleted lines on at least two observed changes exceed a prompt-size-derived threshold.                                                        | Missing diff line counts are not guessed; the rule reports only bounded, explicit line metadata or diff hunks.                                                                                                                                                             |
| Tests before final change without rerun          | A test attempt occurs before the final observed change and no test attempt follows it.                                                              | A test attempt may fail; the signal is about coverage ordering, not test correctness.                                                                                                                                                                                      |
| User correction after unsupported success        | A correction-like user steering message arrives immediately after a success claim without successful verification between them.                     | This is a temporal evidence signal and does not assert why the claim was wrong.                                                                                                                                                                                            |
| Excessive search with little state change        | At least five search commands occur while at most one code change is observed.                                                                      | Search commands are identified by explicit command categories or bounded command names; opaque tool text is not guessed.                                                                                                                                                   |
| Relevant file discovered after implementation    | A changed path is first observed in a file-read event after implementation began.                                                                   | The rule distinguishes observed chronology from repository existence and does not claim the file was unknown to the model.                                                                                                                                                 |

## Rule SDK guarantees

The SDK validates semantic rule versions, nonempty recommendations, unique evidence IDs, disjoint evidence and counter-evidence, single-session input, and the existence of every referenced event before returning findings. Findings and rules are emitted in stable order. Finding UUIDv5 identities derive from the session, rule ID and version, rule-specific stable key, and ordered evidence/counter-evidence IDs. A materially different finding therefore cannot inherit an earlier human review.

The committed corpus contains positive, negative, and edge fixtures for all fifteen rules. Its [precision/recall report](precision-recall.md) describes only those labeled synthetic fixtures and is not a real-world accuracy claim.
